# How is this so fast?

First load: **< 120ms**. Reload: **< 10ms**. No tricks, no CDN magic beyond what Vercel gives you for free. Just Next.js, used correctly.

The core idea is simple: **ship HTML, not JavaScript**.

This guide is specifically for **Next.js apps deployed on Vercel**. The patterns work elsewhere, but the edge caching and build optimizations are Vercel-specific.

---

## The Problem with Most React Sites

Most React apps work like this:

1. Browser requests page
2. Server sends empty HTML shell + JavaScript bundle
3. Browser downloads, parses, executes JavaScript
4. React renders your components
5. User finally sees content

Every step adds latency. A 100KB bundle takes ~100ms just to parse on a mobile device. Then it has to execute.

## The Fix: Server Components

Next.js 13+ defaults to Server Components. They render on the server at build time and send pure HTML. No JavaScript needed to display content.

```tsx
// This is a Server Component by default
// It renders to HTML at build time
export default function Page() {
  return <h1>Hello</h1>
}
```

The browser receives ready-to-display HTML. No waiting for JavaScript.

## What This Site Actually Does

### 1. Force Static Generation

```tsx
// app/page.tsx
export const dynamic = 'force-static'

export default function Personal() {
  return (
    <main>
      <AboutSection />
      <PublicationsSection />
      <ExperienceSection />
      <ProjectsSection />  {/* Only this is client-side */}
      <WorkshopSection />
      <ContactSection />
    </main>
  )
}
```

The `force-static` directive tells Next.js to render this page at build time and cache it globally on Vercel's edge network. When you request the page, you get HTML from an edge server near you. TTFB drops to ~50ms.

### 2. Client Islands (Not Client Pages)

The entire page is server-rendered except one component: the project filter. It needs `useState` for interactivity, so it's a Client Component.

```tsx
// app/components/projects-section.tsx
'use client'

import { useState, useMemo } from 'react'

export function ProjectsSection() {
  const [selectedCategory, setSelectedCategory] = useState('All')
  // Filter logic...
}
```

This is the **Island Architecture** pattern. The page is a static island with tiny interactive islands embedded. Only 3.14KB of route-specific JavaScript ships for this entire page.

### 3. Inline SVGs Instead of Icon Libraries

**Before:**
```tsx
import { Sun, Moon, Monitor } from 'lucide-react'  // ~8KB
```

**After:**
```tsx
const SunIcon = () => (
  <svg width="16" height="16" viewBox="0 0 24 24" fill="none" stroke="currentColor">
    <circle cx="12" cy="12" r="4" />
    <path d="M12 2v2M12 20v2..." />
  </svg>
)
```

Lucide tree-shakes okay, but inline SVGs are zero-dependency and zero-parse-time. For a few icons, it's worth it.

### 4. No Animation Libraries

We removed `motion/react` (~30KB). Animations look nice but they require JavaScript execution before content appears. For a portfolio site, instant load beats smooth entrances.

If you need motion, use CSS:

```css
.card {
  transition: transform 0.2s ease;
}
.card:hover {
  transform: translateY(-2px);
}
```

### 5. Image Optimization

The profile image went from 830KB PNG to 3.9KB WebP:

```js
// Resize to actual display size (56px * 2 for retina = 112px)
await sharp(inputPath)
  .resize(112, 112)
  .webp({ quality: 85 })
  .toFile(outputPath)
```

In the component:

```tsx
<Image
  src="/pranav-optimized.webp"
  width={56}
  height={56}
  priority          // Preload for LCP
  placeholder="blur"
  blurDataURL={blurDataURL}
/>
```

## When to Use This Approach (Tradeoffs)

This method isn't for every site. Here's how to decide:

### Use Static Generation When:

- **Content doesn't change per-request** — portfolios, blogs, marketing pages, documentation
- **SEO matters** — static HTML is immediately crawlable
- **Global audience** — edge caching means fast loads worldwide
- **You want the fastest possible load times**

### Use Dynamic Rendering When:

- **Personalized content** — dashboards, user-specific data
- **Real-time data** — stock prices, live feeds
- **Authentication-gated pages** — content varies per user
- **Frequently updating content** — if ISR revalidation isn't fast enough

### Visual-Heavy Sites (The Hard Tradeoff)

If your site needs:
- Complex entrance animations
- Parallax effects
- Interactive 3D elements
- Heavy motion design

You have two choices:

1. **Accept the JS cost.** Ship the animation library, accept 150KB+ First Load JS. Your LCP will be 2-3s instead of under 1s.

2. **Progressive enhancement.** Load the page static first, then hydrate animations. Users see content instantly, animations load after.

```tsx
// Progressive enhancement example
'use client'
import dynamic from 'next/dynamic'

const AnimatedSection = dynamic(
  () => import('./animated-section'),
  { ssr: false }  // Only load on client
)

export function Page() {
  return (
    <>
      <StaticContent />  {/* Visible immediately */}
      <AnimatedSection /> {/* Loads after hydration */}
    </>
  )
}
```

For portfolio sites, I chose option 3: **no animations**. The site feels fast because navigation is instant, not because of motion design.

## Quick Wins Checklist

1. **Remove `'use client'` from page files.** Move it to the smallest component that needs interactivity.

2. **Add `export const dynamic = 'force-static'`** to pages that don't need per-request data.

3. **Audit your bundle.** Run `npx @next/bundle-analyzer`. Anything over 10KB should justify its existence.

4. **Replace icon libraries with inline SVGs** for icons you use. Three inline SVGs beat importing a library.

5. **Compress images to actual display size.** A 112px image doesn't need 2000px source resolution.
